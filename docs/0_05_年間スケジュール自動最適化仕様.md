# 0_05_年間スケジュール自動最適化仕様

更新履歴
- 2025-12-31: 初版作成。
- 2025-12-31: ボーナス月=2を最優先する最適化目標を追加。

---

## 1. 目的

本仕様は「35日家計簿」における **やりくり費期間** を、
**35日（5週）** と **42日（6週）** の組み合わせで年間（365日/366日）に割り当てるための
自動最適化ロジックを定義する。

- 固定費・特別費は暦月（1ヶ月）で管理する。
- やりくり費は本スケジュール（期間）で管理する。
- 「やりくり費期間が存在しない暦月」は **ボーナス月** とする。

## 2. 入力・出力

### 2.1 入力
- year: 対象年度（例: 2026）
- start_date: 当該年度のスケジュール開始日（例: 2026-01-01）
- week_start: 週の開始曜日（0=Mon..6=Sun）
- constraints（将来拡張）:
  - prefer_42_positions: 42日を置きたい時期の重み付け
  - min_bonus_months / target_bonus_months など

### 2.2 出力
- periods[]: 期間配列
  - period_index
  - days: 35 or 42
  - start_date
  - end_date（start + days - 1）
- derived:
  - bonus_months[]: やりくり費期間が存在しない暦月一覧（year-month）

## 3. 最適化の要件（制約）

## 3.1 最適化の優先順位（確定）

本アプリでは、年間スケジュール生成の最適化目標として **「ボーナス月が2か月になること」** を最優先とする。

- 第1優先：bonus_months の件数が **2** であること
- 第2優先：bonus_months の件数が 2 に最も近いこと（|count-2| 最小）
- 第3優先：42日（6週）期間の数が少ないこと
- 第4優先：期間数（n35+n42）が少ないこと（UI上の複雑さ低減）


1. 年度日数制約
   - sum(period.days) == 365（うるう年は366）
2. 期間長制約
   - period.days ∈ {35, 42}
3. 週境界整合（任意だが推奨）
   - start_date は week_start に揃える（ユーザー設定により未整合も許容）
4. 手動編集整合
   - ユーザーが任意の period を 35↔42 で変更しても、年度日数制約を満たすように再計算できること

## 4. 自動生成アルゴリズム（擬似コード）

### 4.1 基本方針
- まず全期間を35日で敷き詰める。
- 年度日数の不足分を、必要数だけ 42日に変換して埋める。
  - 42日は35日より +7日長い
  - したがって不足分は常に 7 の倍数として解消されるのが望ましい。
- 365/366 を 35 と 42 の線形結合として満たす組を探索する。

### 4.2 組み合わせ探索

### 4.2.1 候補の評価（ボーナス月=2を最優先）

候補 (n35, n42) が年度日数制約を満たしても、**42日の配置**によってボーナス月の件数が変化しうる。
そのため、候補ごとに「初期配置（分散配置）」を生成して bonus_months を算出し、以下のスコアで比較する。

```
bonus = count(bonus_months)
score = (
  1000 * abs(bonus - 2)   # 最優先：ボーナス月が2からどれだけ離れているか
  + 10 * n42              # 次点：42日数を抑える
  + 1 * (n35 + n42)       # 期間数を抑える
)
```
- `abs(bonus-2)` が同じ場合は、n42 が小さい方を採用する。
- それでも同点の場合は、期間数が少ない方を採用する。
```

```
total_days = is_leap(year) ? 366 : 365
best = null

for n42 in range(0, 60):                 # 上限は安全側（実際はもっと小さい）
    for n35 in range(0, 60):
        if 42*n42 + 35*n35 == total_days:
            candidate = (n35, n42)
            # 評価関数: できるだけ 42 を少なく、期間数を少なく等
            score = w1*n42 + w2*(n35+n42)
            if best is null or score < best.score:
                best = candidate
```
- best が見つからない場合はエラー（設計上は必ず見つかる前提で検証する）。

### 4.3 期間配置（シード生成）

#### 4.3.1 42日配置の探索（簡易）

初期実装では、42日を等間隔に分散させる配置を1案生成する。
ただし、ボーナス月が2にならない場合に備え、次の探索を行う。

- 42日の配置をシフトさせた複数案を生成（例：先頭から 0..(N-1) 期間分ずらす）
- 各案について bonus_months を算出し、`abs(count-2)` が最小の案を選ぶ
- 同点なら 42日の偏りが小さい案（最大連続35回数が大きい等）を選ぶ

この探索は「手動編集可能」という前提のもと、計算量を抑えた簡易実装でよい。

```
(n35, n42) = best
periods = [35]*n35 + [42]*n42

# 42日の配置を分散させる（偏りを避ける）
periods = distribute(periods)   # 例: 42 を等間隔に挿入

# 日付を割り当て
cursor = start_date
for i,days in enumerate(periods):
    p[i].start = cursor
    p[i].end = cursor + (days-1)
    cursor = cursor + days
```
distribute() の例：
- 42がk個あるなら、全期間長 N の中でほぼ等間隔に配置する。
- 初期実装は「等間隔 + 端の調整」でよい。

## 5. 手動編集（35↔42）時の補正

ユーザーが period[j] を変更したとき、総日数が年度日数からズレる場合がある。

### 5.1 補正ルール（推奨）
- まず変更後の総日数差分 `delta = total - target` を計算する。
- delta が +7 の倍数なら、他の期間を必要数だけ 42↔35 で反転して補正する。
- 反転対象の選択規則
  - ユーザーが直近で操作した期間の近傍は避ける
  - 42が偏らないよう分散を維持する
  - bonus_months の数を極端に減らさない（将来の評価関数）

### 5.2 擬似コード
```
target = is_leap(year) ? 366 : 365
delta = sum(periods.days) - target

while delta != 0:
    if delta > 0:
        # 余っている => 42 を 35 に戻す（-7）
        idx = choose_convertible_period(days=42)
        periods[idx].days = 35
        delta -= 7
    else:
        # 足りない => 35 を 42 にする（+7）
        idx = choose_convertible_period(days=35)
        periods[idx].days = 42
        delta += 7

recompute_dates(periods, start_date)
```

## 6. ボーナス月判定

### 6.1 定義
- 暦月（yyyy-mm）に対して、やりくり費期間の「所属日」が0日の月をボーナス月とする。

### 6.2 実装イメージ
```
covered_days = set(all dates covered by periods)
for month in 1..12:
    if count(d in month where d in covered_days) == 0:
        bonus_months.add(month)
```

## 7. テスト観点（最小セット）

### 7.1 自動生成
1. 平年（365日）で `sum(days)==365` を満たすこと
2. うるう年（366日）で `sum(days)==366` を満たすこと
3. 全期間が 35 or 42 のみであること
4. 期間の start/end が連続し、重複・欠損がないこと

### 7.2 手動編集
1. 35→42 を1回行っても、補正後に年度日数制約を満たすこと
2. 42→35 を1回行っても、補正後に年度日数制約を満たすこと
3. 編集後に期間境界が再計算され、start/end が連続すること

### 7.3 ボーナス月
1. bonus_months が0以上で算出されること
2. ボーナス月に属する取引は「ボーナス支出」カテゴリで記録できること（別仕様の結合テスト）

---


### 7.4 ボーナス月=2（初期スケジュール）
1. 自動生成した初期スケジュールで bonus_months の件数が **2** であること
2. ユーザーが手動編集して bonus_months が2以外になった場合でも、UI上で正しく再計算・表示されること
